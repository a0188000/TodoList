# 簡報逐頁重點稿

搭配 `docs/ai-pipeline-slides.html` 使用。每頁分成三部分:
- **必講**:2–3 句,時間不夠只講這些。
- **數據**:可以引用的實際紀錄,不是每頁都有。
- **轉場**:接到下一頁的一句話。

## 實際執行數據總覽

**資料來源**
- `TodoList-pipeline/pipeline/state/tickets.json`
- `pipeline/state/logs/SID-*/*.log`:每一輪結束時的 `🏁 turns / cost` 與 `⏹ exit` 紀錄
- git 歷史:`git show --stat`

**使用前先知道的限制**
- 樣本只有 3 張票、13 輪執行,只能說明「實際跑過、發生過什麼」,不能推論成功率或平均效益。
- `cost` 是 Claude Code 在每輪結束時回報的數值。這段期間曾遇到 session 額度上限,代表使用的是訂閱方案,所以這個數字**不等於實際帳單**。
- 沒有「人工開發同樣功能要多久」的基準,因此**無法計算節省的時間**。
- 時間是從派工到 process 結束的實際經過時間,包含 build、測試、模擬器等待。

| 票 | 標題 | 輪數 | 規格階段 | 停下到送出審核 | 實作階段 | 測試 | 驗證截圖 | 功能 commit | 目前狀態 |
|---|---|---|---|---|---|---|---|---|---|
| SID-1 | 新增 TODO List | 5 | 10.5 分 / 29 turns / $2.49 | 約 5 分(approve,無留言) | 22.9 分 / 150 turns / $6.89 | 22 | 8 張 | 25 檔 +1798 / −48 | Jira 完成 |

- 13 輪的 log 全部記錄為 `model=claude-opus-5-5`。依任務輕重切換模型的功能(commit `a3465bb`,09-28 19:28)加入之後,紀錄中還沒有觸發過改用 Haiku 的情況。

### 可以講的真實事件

1. **權限被擋,催生第二層防護(SID-1)**
   - 第一輪只跑 0.8 分鐘就寫出 `blocked.json`。原因是 worktree 沒被 Claude Code 信任,`.claude/settings.json` 的 27 條 allow 規則全部被忽略,所有 `jira` 指令都被拒絕。
   - agent 在 `human_action` 寫出具體的修法。
   - 約 12 分鐘後我提交 `9ad8514`,改成把權限清單以 CLI 參數明確傳入。
   - 第二輪重派之後正常產出規格。
2. **卡住時自動終止(SID-2)**
   - 規格核准後的實作輪次中,`@code-reviewer` subagent 被中斷(16:05 → 17:19)。之後 15 分鐘沒有任何輸出,orchestrator 判定卡住,終止了 process(exit 143)。
   - 因為 Jira 狀態已經變成 In Development,這張票被自動重新排入。
   - 下一輪執行 55.5 分鐘後被我手動停止;log 沒有記錄停止的原因。
   - 再下一輪 8.8 分鐘完成交付,40/40 測試通過。
3. **額度用完時停在 idle,等人接手(SID-3)**
   - 實作輪次一開始就遇到 session 額度上限,exit 1,票停在 `idle`。
   - 額度重置後我手動繼續,1.8 分鐘內完成驗證並交付,43/43 測試通過。
4. **測試數隨功能累加**:22 → 40 → 43。每張票都在既有測試全數通過的前提下交付。

## 第 1 頁 封面

- **必講**
  - 這是我在 TodoList iOS 專案上實際在跑的 AI 開發流程。
  - 核心理念:機械性工作交給 AI,判斷留給人。
  - 下面四個欄位就是目前 Jira 看板實際的流程。
- **數據**:跑過 3 張真實 Jira 票(SID-1~3),其中 1 張已完成、1 張已 merge。
- **轉場**:先用 30 秒講完全貌。

## 第 2 頁 30 秒版本

- **必講**
  - 照投影片那段話唸。
  - 三個數字各代表一個設計重點:1:1 worktree 是隔離,3 種 signal file 是溝通協定,2 道人工關卡是信任邊界。
- **數據**:3 張票、13 輪執行,全部留有 log。
- **轉場**:第一個設計問題是「哪些該交給 AI」。

## 第 3 頁 分工

- **必講**
  - 判斷標準:能用證據驗證的交給 AI,需要負責任的決定留給人。
  - 功能票的 PR 由 RD 自己開,agent 只推分支。
- **數據**:三張票的規格都是由人核准之後才進入實作。停下到送出審核分別約 5、14、2 分鐘。
- **轉場**:分工確定後,系統由五個元件組成。

## 第 4 頁 架構

- **必講**
  - orchestrator 是只用標準函式庫的 Python server,負責排程、派工、收尾、寫入審核結果。
  - 每張票在自己的 git worktree 裡跑 `claude -p`。
  - agent 不呼叫 API,結束前寫 JSON 檔。
- **數據**:目前 `~/code/ai-demo-workspaces/` 下有 SID-2、SID-3 兩個 worktree 並存,互不影響。
- **轉場**:看一張票實際怎麼走一輪。

## 第 5 頁 一輪流程

- **必講**
  - 逐步點亮 01–06。
  - 重點是 04「停下」:agent 做完一個階段就結束 process,不會掛著等人。
  - 下一輪是全新的 session,從 workpad、ledger 和決策檔重建上下文。
- **數據**:SID-3 走完一個完整循環:規格 6.4 分 → 審核約 2 分 → 實作 5.2 分 → 交付。中間因為額度上限停過一次(事件 3)。
- **轉場**:agent 怎麼知道這一輪要做什麼?看 Jira 狀態。

## 第 6 頁 狀態路由

- **必講**
  - Jira 狀態就是 agent 的路由表。
  - 灰色兩列(Code Review、Rework)已經寫好流程,但看板上還沒有這些欄位,**沒實際跑過**。
  - 這裡的 Code Review 是 handoff 之後 RD 審 PR 的 Jira 欄位,agent 只查 CI。
- **數據**:13 輪的派工狀態都是 待辦事項、SA/SD、In Development 三種,沒有 Code Review 或 Rework。
- **轉場**:orchestrator 內部也有自己的狀態機。

## 第 7 頁 狀態機

- **必講**
  - running 之後往哪走,由 agent 留下哪個 signal file 決定。
  - 虛線是自動機制:沒留 signal 就自動續跑,Jira 狀態變了就重新排入。
- **數據**:13 輪的結束狀態有 awaiting_review 3 次、handed_off 5 次、blocked 1 次、queued 2 次、stopped 1 次、idle 1 次。
- **轉場**:其中最關鍵的是 signal file 這個設計。

## 第 8 頁 Signal file

- **必講**
  - agent 和 orchestrator 之間沒有 API,只有檔案。
  - 讀取後搬到 history,每個檔案只處理一次。
  - 代價是 agent 不能中途發問。
- **數據**:SID-3 的 `.pipeline/history/` 留有 `discussion_request.json` 與 `handoff.json` 的歸檔,每一輪留下什麼都查得到。
- **轉場**:agent 停下來之後,人要怎麼把意見傳回去?

## 第 9 頁 人工審核

- **必講**
  - RD 可以針對規格的某一章節留言。
  - 三種決定分別對應三條路。
  - 多輪審核的上下文靠 `discussion_history` 延續。
- **數據**:SID-2 的審核留有 1 則章節留言加總評,agent 在下一輪處理。三張票都在第一輪 approve,所以 request_changes 和 reject **還沒實際發生過**。
- **轉場**:核准之後,怎麼確保 agent 不跳過步驟?

## 第 10 頁 Anti-skip ledger

- **必講**
  - agent 最常見的問題是宣稱做完了但其實跳過。
  - 所以有 10 個 gate,每一格都要附證據。
  - 主動說明限制:目前只靠 prompt 約束,程式沒有檢查。
- **數據**:SID-3 第一輪的 log 可以看到 ledger 逐項填了證據,例如 `jira summary SID-3` 的結果。
- **轉場**:另一個風險是安全。

## 第 11 頁 安全

- **必講**
  - Jira 內容一律當作不可信輸入。
  - 三層限制:prompt 區分任務意圖與控制指令、工具白名單與黑名單、禁止 shell 展開。
  - 目的是降低風險,不是保證。
- **數據**:事件 1(SID-1 權限被擋)。第二層防護「權限用 CLI 參數明確傳入」就是在這次實際碰到問題後修正的(commit `9ad8514`)。
- **轉場**:接下來是 iOS 才會遇到的問題。

## 第 12 頁 iOS

- **必講**
  - `ios-build` 讓 agent 能穩定操作 Xcode。
  - exit 2 用來區分「沒有測試」和「測試失敗」。
  - 截圖用驗收條件編號命名,當作驗收證據。
  - 因為需要本機 Xcode 和模擬器,orchestrator 跑在本機。
- **數據**:三張票共留下 19 張驗證截圖(8、7、4)。測試數 22 → 40 → 43,每次交付都全數通過。
- **轉場**:講完設計,來看實際跑起來的紀錄。

## 第 13 頁 實際執行紀錄

- **必講**
  - 前面講設計,這頁是實際跑過的紀錄:3 張真實 Jira 票,13 輪執行,每一輪都有 log。
  - 下面三個事件,每一個都是前面某個機制真的被觸發:blocked、卡住偵測、停在 idle 等人。
  - 樣本很小,不談成功率,也不估算省了多少時間。
- **數據**:整頁都是數據,見本文件開頭的總覽表與事件 1–3。
- **轉場**:這些事件背後,是下一頁的幾個護欄設定。

## 第 14 頁 可靠性與成本

- **必講**
  - 15 分鐘沒輸出就終止;自動續跑上限 2 次;單一 session 上限 200 turns。
  - 超過上限就停下來等人,不會無限重試。
- **數據**
  - 事件 2:卡住自動終止實際觸發過 1 次。
  - 事件 3:額度用完後停在 idle 等人。
  - 13 輪中有 11 輪回報 cost,合計 $21.32(Claude Code 回報值,非實際帳單)。
  - 單輪最高是 SID-1 的實作輪次:150 turns、$6.89。
  - 改用 Haiku 的模型切換,紀錄中還沒觸發過。
- **轉場**:把這些設計的取捨整理成一張表。

## 第 15 頁 取捨

- **必講**
  - 只挑一兩列講,建議選「用檔案溝通」和「流程規則放在 repo」。
  - 講的時候好處和代價一起講。
- **數據**:流程規則本身也經過 commit 修改,例如 `48d30b5` 對應 SID 的 Jira 狀態、`a3465bb` 依任務輕重切換模型,改流程就跟改程式一樣有紀錄。
- **轉場**:最後講目前的限制。

## 第 16 頁 反思

- **必講**
  - gate 只靠 prompt;沒有量化成效;CI 未設定;一次只跑一張票。
  - 下一步:由程式檢查 ledger、記錄每一輪的數據。
- **數據**:可以說「目前已經有 13 輪的 log,cost 和 turns 都有記錄,但還沒做成統計,也沒有人工開發的基準可以比較」。
- **轉場**:最後是幾個預期的追問。

## 第 17 頁 預期追問

- **省多少時間?** 沒有人工基準,不給數字。可以講實際經過的時間:SID-3 從規格到交付,agent 執行時間約 13 分鐘(6.4 + 5.2 + 1.8),另外還有人工審核和額度中斷的等待。
- **成本多少?** Claude Code 回報 11 輪合計 $21.32。使用的是訂閱方案,這不是實際帳單。
- **成功率?** 樣本只有 3 張,不談成功率。三張都有交付,途中遇過 blocked、卡住、額度上限各一次,都由機制接住後再由人接手。
- **收尾**:設計 AI 系統的重點不在 prompt 寫多漂亮,而在狀態、停止點和信任邊界要清楚。
